# ios-shortcuts: Pages site of iCloud shortcut install links

Site: https://poeggi.github.io/ios-shortcuts/ (GitHub Pages from main, path /).
The site is data-driven: `index.html` renders `shortcuts.json`; each published
shortcut is one json entry (`icloud` field).

## Publishing workflow

- Shortcuts are built by hand in the Shortcuts app, then shared via
  long-press > Share > Copy iCloud Link. iCloud links are snapshots: editing a
  shortcut requires re-sharing and replacing the link.
- Publishing is never just a shortcuts.json entry. ALWAYS also download and
  analyse the published shortcut and write an accurate action-by-action
  description. `tools/fetch-shortcut.py` does it:

      python tools/fetch-shortcut.py            # all
      python tools/fetch-shortcut.py <slug>     # one
      python tools/fetch-shortcut.py --check    # verify archive vs live, no writes

- Archive a copy of every shortcut in the repo. One folder per shortcut,
  `shortcuts/<slug>/`: hand-written `README.md`, GENERATED `sequence.md`
  (resolved action list + record metadata), `<slug>.plist` (readable XML,
  diffable, NOT installable), `<slug>.shortcut` (Apple-signed, installable,
  opaque, cert expires ~13 months), `<slug>.png` (the rendered 450x450 icon).
  The site's Mirror button serves the .shortcut and the card shows the .png,
  both derived from the slug, so the archive MUST exist or the button 404s and
  the card looks broken.
- Every shortcut ships its icon; `<slug>.png` is NOT optional. The plist's
  `WFWorkflowIcon` holds only a glyph number + colour, no image; the real logo
  is the record's third asset (`icon`). `WFWorkflowIconStartColor` is RGBA not
  ARGB; decode as `(raw & 0xFFFFFFFF) >> 8` (an ARGB read gives wrong colours).

## Site architecture (keep it this way)

- `style.css` holds every token (--icon, --ctl-h, --radius-*, --indent,
  --var-bg) and `render.js` holds every renderer (header/buttons/stepsHtml/
  detail/mountDetail). Root `index.html` and each `shortcuts/<slug>/index.html`
  carry NO styling.
- The per-shortcut page is GENERATED by fetch-shortcut.py and is only
  link-preview metadata plus `mountDetail("<slug>")`. Never hand-edit a
  generated page. A page one level down sets `window.BASE = "../../"` before
  loading render.js.
- The detail page draws the action list like the Shortcuts editor (bold action
  name, variable tokens, params underneath, control flow indented) from
  `sequence.json`. Variables are marked OUT OF BAND with chr(2)/chr(3), not
  with brackets: a bracket convention wrongly chipped the literal [\s\S] inside
  a regex parameter. flat() renders markers for sequence.md; pieces() splits
  them into {"t":"var"|"text"} segments for the JSON.
- Non-Apple actions are named by the generator from the last dotted identifier
  segment, with the source app shown (e.g. "Is Call Active" from the free App
  Store app Actions by Sindre Sorhus, required by busy-redialer).
- Link previews: og/twitter meta on the root and on every generated shortcut
  page. The root uses generated `og.png` (1200x630, built with Pillow by
  write_og_image, summary_large_image); a shortcut page uses its own 450x450
  icon (card type summary).

## iCloud record API (what the tooling rests on)

Any shared shortcut can be read back and downloaded from
`https://www.icloud.com/shortcuts/api/records/<id>` (plain GET, no auth). The
JSON has `fields.name`, `signingStatus`, `signingCertificateExpirationDate`
(~13 months out) and two ASSETID download URLs: `shortcut` (binary plist ->
plistlib -> full action list) and `signedShortcut` (installable). Substitute
the literal `${f}` in downloadURL with any filename; those URLs expire in
minutes, the record does not. Re-sharing ALWAYS mints a new record id; a link
can never be updated in place. Superseded shares stay live until revoked from
the Shortcuts app on-device; there is no revocation API.

## iOS signing facts (hard-won, do not relitigate)

- Unsigned `.shortcut` files cannot be imported since iOS 15. Passing their URL
  to `shortcuts://import-shortcut` gives "the shortcut URL provided was
  invalid"; content-type and URL encoding are NOT the cause.
- "Allow Untrusted Shortcuts" does NOT lift this; it governs already-signed
  shortcuts.
- On-device Share > File > Anyone makes Apple's servers sign the file, so a
  signed installable file needs no Mac.
- Claude's iOS app cannot build or install shortcuts. It does expose an
  "Ask Claude" App Intent usable as an action INSIDE a shortcut (iOS 18+).

## Per-shortcut do-not list

- pdf-export: verified correct on-device even though the plist reads otherwise
  (Ask default answer points at the getitemname UUID, Don't Include File
  Extension off). Do NOT re-raise either as a defect. Its README intentionally
  carries no Known-issues section.
